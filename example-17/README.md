# Example 17 - 일회용 CSRF 토큰 (Punk + Perl)

세션 기반 **일회용 CSRF 토큰**을 시연하는 예제입니다. 안전하지 않은 메서드
(POST/PUT/PATCH/DELETE)는 살아있는 토큰이 있어야 통과하며, 한 번 쓰면 소비됩니다.

- `session ...` + `csrf` — 세션 위에 토큰 계층 활성화
- `$c->csrf_token` — 현재 토큰 값 (폼/헤더로 전달)
- 기본 헤더 `X-CSRF-Token`, 폼 필드 `_csrf`, 쿠키 미러 `csrf`

## Routes

| Method | Path            | Description |
|--------|-----------------|-------------|
| GET    | /api/ping       | ping/pong |
| GET    | /api/healthz    | k8s liveness |
| GET    | /api/readyz     | k8s readiness |
| GET    | /api/token      | `csrf_token` 발급 (세션 쿠키 동반) |
| POST   | /api/action     | `X-CSRF-Token` 필요, 사용 시 소비 |

## 동작 방식 (왜 이렇게 될까)

### 토큰은 세션에 산다

CSRF 토큰은 **세션(=서명 쿠키)** 안에 저장됩니다. 그래서 별도 서버 저장소가
필요 없고, 토큰을 회전시키는 비용도 없습니다 — 세션을 더럽히면 세션 자체의
되쓰기가 쿠키를 다시 서명해 줍니다. `csrf` 를 `session` 없이 켜면 `to_app` 에서
croak 합니다(토큰이 살 곳이 없으므로).

### 일회용 = 회전

안전하지 않은 요청이 통과하면 그 검사가 **토큰을 새 값으로 교체**합니다. 그래서
같은 토큰으로 두 번은 통과하지 못합니다(두 번째는 403). 기본은 토큰 하나만
살아있고, `keep => N` 으로 N 개까지 동시에 살려둘 수 있습니다(여러 탭 대응).

### 무엇을 검사하나

POST / PUT / PATCH / DELETE 만 검사합니다. GET/HEAD/OPTIONS 는 검사하지 않습니다
(상태를 바꾸지 않아야 하고, URL 에 담긴 토큰은 Referer·히스토리로 샙니다).
`Authorization` 헤더가 있는 요청은 건너뜁니다(브라우저가 자동으로 붙이지 않으므로
CSRF 대상이 아님).

### "신선도" 이지 "완전한 1회성 증명"은 아니다

서버측 저장소가 없으므로 소비 기록을 남기지 않습니다. 위조 토큰 단독 재생은
거부되지만(세션이 이동했으므로), **예전 세션 쿠키 + 짝 토큰 전체**를 재생하면
통과할 수 있습니다. CSRF 방어로는 충분한 트레이드오프이며, 도난당한 쿠키 자체에
대한 방어는 `secure`/`httponly`/`samesite` 의 몫입니다.

### 세션 없이 못 쓴다

`csrf` 는 `session` 에 의존합니다. 이 예제는 세션과 CSRF 를 함께 켭니다.

## Notes

- 테스트는 토큰 발급 → 무토큰 403 → 유효 토큰 200 → 재사용 403 순으로 검증합니다.
