# Example 90 - 멱등성 키 (Idempotency-Key) (Punk + Perl)

네트워크 재시도로 **같은 결제가 두 번 생성되는 일**을 막는 멱등성 키 예제입니다. 같은 키로
같은 요청을 다시 보내면 **원래 응답을 그대로 재생**합니다.

- `POST /payments` + `Idempotency-Key` 헤더
  - 처음 → `201`, 결제 생성
  - 같은 키 + 같은 본문 → **재생**(동일 응답, `Idempotency-Replayed: true`)
  - 같은 키 + 다른 본문 → `409`
- `GET /payments` / `GET /payments/:id`
- 키가 없으면 그냥 매번 생성(비멱등)

## Routes

| Method | Path           | Description |
|--------|----------------|-------------|
| GET    | /api/ping      | ping/pong |
| POST   | /payments      | 결제 생성 (멱등 키 선택) |
| GET    | /payments      | 목록 |
| GET    | /payments/:id  | 단건 |

## 동작 방식 (왜 이렇게 될까)

### 왜 필요한가

클라이언트가 결제 요청을 보냈는데 **응답이 유실**되어 다시 보내면, 결제가 두 번 됩니다.
키를 함께 보내면 서버가 "이미 처리한 요청"임을 알아채고 **처음 결과를 재사용**합니다.

### 키 + 본문 지문(fingerprint)

키만 저장하면, 실수로 **다른 내용**을 같은 키로 보냈을 때 잘못된 결과를 재생하게 됩니다.
그래서 본문의 해시(지문)를 함께 저장하고 대조합니다.

```perl
my $fp = sha256_hex(canonical($body));
if ($IDEM{$key}{fp} ne $fp) { return 409 }
```

같은 키 + 같은 지문 → 재생, 같은 키 + 다른 지문 → `409`.

### 재생 여부를 헤더로 알린다

클라이언트가 "이건 원래 처리 결과의 재생"임을 알 수 있게 `Idempotency-Replayed: true` 를
붙입니다.

### 실패한 요청은 저장하지 않는다

검증 실패(`400`) 같은 요청은 키에 기록하지 않습니다. 그래야 클라이언트가 **고쳐서 같은
키로 다시 시도**할 수 있습니다.

### 왜 재생에도 같은 상태코드를 주나

재시도한 클라이언트 입장에서는 원 요청이 성공했든 실패했든 **동일한 결과**를 받아야
합니다. 그래서 저장한 상태코드(`201`)를 그대로 돌려줍니다.

## Notes

- 실전에서는 키-응답을 TTL(예: 24시간)과 함께 외부 저장소에 둡니다.
- 동시에 같은 키가 들어오는 경우를 대비해 **원자적 삽입**(있으면 읽기)이 필요합니다.
- 테스트는 생성/재생/충돌/다른 키/목록 불변/실패 후 재사용을 검증합니다.
