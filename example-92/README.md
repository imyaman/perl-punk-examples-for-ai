# Example 92 - 경로 기반 API 버전관리 (Punk + Perl)

`/v1`, `/v2` 처럼 **URL 경로로 버전을 나누고**, 구 버전에 **폐기 예고 헤더**를 붙이는
예제입니다. `/version` 으로 지원 버전을 알려줍니다.

- `GET /v1/users` → 구 응답 형식(배열) + `Deprecation`/`Sunset`/`Link`
- `GET /v2/users` → 현 응답 형식(객체 + `meta`)
- `GET /version` → 현재/지원/폐기 버전

## Routes

| Method | Path         | Description |
|--------|--------------|-------------|
| GET    | /api/ping    | ping/pong |
| GET    | /v1/users    | 구 버전 (폐기 예정) |
| GET    | /v2/users    | 현 버전 |
| GET    | /version     | 버전 정보 |

## 동작 방식 (왜 이렇게 될까)

### 버전을 올리는 응답 형식 변화

v1 은 이름 배열, v2 는 객체 + 메타입니다. 같은 자원이라도 표현이 바뀌면 **호환성**을
지키기 위해 버전을 나눕니다.

```perl
# v1
$c->json({ users => [ map { $_->{name} } @USERS ] });
# v2
$c->json({ data => \@USERS, meta => { count => ..., version => 'v2' } });
```

### 폐기 예고는 헤더로

서버가 조용히 v1 을 없애면 클라이언트가 갑자기 깨집니다. 구 버전 응답에 다음을 붙입니다.

| 헤더 | 의미 |
|------|------|
| `Deprecation: true` | 더 이상 권장하지 않음 |
| `Sunset: <date>` | 종료 예정일 |
| `Link: ...; rel="successor-version"` | 대체 버전 안내 |

### `/version` 으로 발견 가능하게

클라이언트가 하드코딩 대신 **지원 버전·현재 버전·폐기 정보**를 조회하도록 합니다.

### 경로 버전 vs 헤더 버전

경로(`/v2`)는 **캐시·로그·라우팅이 명확**합니다. 헤더나 쿼리 버전은 URL 을 깔끔하게
유지하지만 캐싱(특히 `Vary`)이 까다롭습니다. 여기서는 경로 방식을 씁니다.

### 지원하지 않는 버전은 `404`

`/v3/users` 는 라우트가 없어 자연히 `404` 입니다. 별도 핸들러로 **명시적 안내**를 줄 수도
있습니다.

## Notes

- 신·구 버전은 보통 같은 핸들러를 공유하고 **직렬화만** 분기합니다(중복 로직 방지).
- 폐기 기간을 두고 사용량을 모니터링한 뒤 종료합니다.
- 테스트는 v1/v2 형식/폐기 헤더/버전 발견/미지원 404를 검증합니다.
