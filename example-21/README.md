# Example 21 - HMAC 서명 검증 (웹훅) (Punk + Perl)

요청 본문을 **HMAC-SHA256** 으로 서명·검증하는 예제입니다. 결제사 웹훅처럼
"공유 비밀로 서명된 요청"만 받는 흐름을 구현합니다.

- `X-Signature: sha256=<hmac_sha256_hex(body, secret)>` 검증
- 서명 대상은 **원문 본문** (`$c->req->body`)
- 비교는 **상수 시간**(길이 동일 시 바이트별 XOR 누적)

## Routes

| Method | Path             | Description |
|--------|------------------|-------------|
| GET    | /api/ping        | ping/pong (공개) |
| GET    | /api/healthz     | k8s liveness |
| GET    | /api/readyz      | k8s readiness |
| POST   | /webhook/event   | `X-Signature` 검증 필요 |

서명: `HMAC-SHA256(body, 'webhook-shared-secret')`

## 동작 방식 (왜 이렇게 될까)

### 본문을 그대로 서명한다

서명은 **수신한 원문 바이트**에 대해 계산해야 합니다. JSON 으로 다시 직렬화하면
키 순서·공백이 달라져 서명이 어긋납니다. 그래서 `$c->req->body` 를 그대로 씁니다.
검증을 통과한 뒤에야 `$c->req->json` 으로 파싱합니다.

### 전체를 덮는 무결성

서명이 본문 전체를 덮으므로, 공격자가 본문을 조금이라도 바꾸면 HMAC 이 달라져
거부됩니다(테스트의 "tampered body" 케이스). 서명 없이 본문만 보내도 거부됩니다.

### 타이밍 공격 방어

`eq` 대신 **상수 시간 비교**를 씁니다. 바이트마다 XOR 해 누적하고, 모든 바이트를
끝까지 비교한 뒤 판정합니다. 길이가 다르면 즉시 0 이지만, 같은 길이에서는 비교
시간이 값에 의존하지 않습니다.

### 비밀은 설정에서

여기선 리터럴이지만, 운영에서는 `secret('webhook_secret')` 처럼 secrets 시스템에서
가져옵니다. 서명 비밀은 코드에 두지 않습니다.

### 인증과의 차이

Bearer/Basic(예제 19·20)은 "누가 보냈는가"를 묻고, HMAC 은 "이 본문이 진짜이며
변조되지 않았는가"를 묻습니다. 웹훅은 후자가 목적입니다.

## Notes

- `--data-raw` 로 보낸 본문을 그대로 서명/검증합니다. 실제로는 타임스탬프를 서명에
  포함해 재생 공격을 막는 것이 일반적입니다.
